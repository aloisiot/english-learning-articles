# 02 — Platform dependence

> **The question:** How tightly does adopting Supabase Auth bind this
> system to Supabase, how portable does it stay, and how hard would a
> later migration be?

**Short answer:** less tightly than most hosted auth, because **the
identity records live in your own Postgres rather than in the vendor's
database** — and that single fact is what makes the others answerable.
The lock-in that matters is not the data. It is authorisation logic
expressed as Supabase-specific SQL, and SDK calls scattered through
application code. Both are avoidable by decisions taken now, at a cost of
roughly one indirection layer.

---

## 1. What Supabase Auth actually is

It is **GoTrue**, an open-source authentication server, writing to an
`auth` schema **inside the Postgres database you already own**. Users,
identities, sessions and refresh tokens are rows you can `SELECT`.

This is the structural difference from Clerk, Auth0 and similar: those
hold your users in *their* database and expose them through an API. You
cannot dump them, you cannot join against them, and leaving means
exporting through whatever their API permits. With Supabase, `pg_dump`
takes the users with everything else.

**Confidence: high** on the architecture; GoTrue's open-source status and
the `auth` schema are load-bearing here and are in the register.

## 2. The five coupling points, worst first

| # | Coupling | Why it binds | Cost to unpick |
|---|---|---|---|
| 1 | **RLS policies calling `auth.uid()` / `auth.jwt()`** | These are Supabase-provided SQL functions. On plain Postgres they do not exist. If they are your only authorisation, your security model is written in a dialect only Supabase speaks. | Rewrite every policy, or re-implement the functions |
| 2 | **`@supabase/supabase-js` call sites** | Mechanical, but the cost scales with how far it spreads. A call in every component is a migration through every component. | Proportional to spread — controllable |
| 3 | **Foreign keys to `auth.users.id`** | Your domain tables reference vendor-managed rows. Swap providers and every key is orphaned. | One column, if isolated; every table, if not |
| 4 | **Session handling** — refresh tokens, cookie helpers, JWT claim shape | Provider-specific, and the Next.js helpers are opinionated about where the session lives. | Contained, if kept in one module |
| 5 | **Configuration** — email templates, redirect URLs, provider secrets | Not code. Re-entered by hand elsewhere. | Hours, not architecture |

Points 1 and 2 are the real exposure. Points 3–5 are bounded.

## 3. Four decisions that keep it portable

Each is cheap now and expensive later.

**a. The browser never talks to Supabase directly.** All data access goes
through the class app's route handlers. This app already has a server and
already holds every secret there — see
[`07`](../video-calls/07-two-app-architecture.md) §1, where making the
class app a server *removed* a vendor. Keeping the SDK server-side
collapses coupling point 2 from "everywhere" to "one layer", and it is
the same decision the repo has already made twice.

**b. Own your primary key.** The conventional pattern makes
`profile.id = auth.users.id`, so the vendor's UUID becomes the key every
other table references. Instead:

```
profile
  id            uuid  primary key   -- ours, generated by us
  auth_user_id  uuid  unique        -- theirs, the only vendor reference
```

Every domain foreign key points at `profile.id`. Changing identity
provider then rewrites **one column in one table**. The cost is a join in
RLS policies (`profile.auth_user_id = auth.uid()` rather than
`profile.id = auth.uid()`) and one extra lookup per request.

**c. Authorisation lives in application code; RLS is defence in depth.**
This is the most important one and the easiest to get backwards. RLS is
genuinely excellent, and the temptation is to make it the whole security
model. Do that and leaving Supabase means rewriting your security model
from scratch, under time pressure, at the moment you are already
migrating. Put the rules in server code that any Postgres can back, and
keep RLS underneath as a second wall. Then losing RLS costs you a safety
net, not the model.

**d. Auth behind one module.** A `class/server/auth.ts` exposing
`currentUser()`, mirroring what `class/server/config.ts` already does for
environment and `class/server/daily.ts` does for Daily. The house pattern
is already "the only place that talks to X"; identity becomes the third.

## 4. How hard a migration actually is

Assuming the four decisions above:

| Layer | Difficulty | Why |
|---|---|---|
| Domain data | **Trivial** | It is Postgres. Dump, restore. |
| User records | **Easy** | Rows in your own database. GoTrue stores bcrypt password hashes, which most systems accept — so passwords survive. |
| Magic-link-only users | **Free** | They have no password to migrate. They re-authenticate. |
| Sessions | **Free** | Everyone logs in again. Annoying once, not a data problem. |
| RLS policies | **Moderate** | Rewrite, or drop — survivable precisely because of decision (c). |
| Application code | **Low** | One auth module, one data layer. |

Without those decisions, the same migration is a rewrite.

**The escape hatch that makes this materially safer than the
alternatives: GoTrue can be self-hosted.** Running it yourself against
the same Postgres is not really a migration at all — the schema is
already the right shape. That path also resolves the inactivity-pause
risk, which is otherwise the strongest argument against Supabase
([`05`](../video-calls/05-accounts-and-access.md) §2).

## 5. The portability tax, stated plainly

One extra column, one join in each policy, and a discipline about where
the SDK may be imported. That is the whole bill. It is small enough that
the honest recommendation is to pay it — not because Supabase is likely
to be abandoned, but because the same decisions produce a better-factored
system regardless, and this repo has already twice benefited from putting
one concern behind one module.

**What is *not* worth doing:** an abstraction layer that hides Supabase
behind a home-made interface capable of swapping providers. That designs
an abstraction against one caller, which
[`08`](../video-calls/08-implementation-plan.md) already rejects for
`lib/`, and it is the reason vendor-agnostic layers usually leak anyway.
